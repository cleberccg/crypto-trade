Descrição técnica:
  Complete project scaffold implemented following the specified modular
  architecture. All modules are decoupled and communicate through well-defined
  interfaces (Abstract Base Classes).

  Key architectural decisions:
  1. Config uses frozen dataclasses loaded from .env via python-dotenv.
     Immutability prevents accidental config mutation at runtime.
  2. Logger factory (get_logger) is the single entry point for all logging.
     RotatingFileHandler prevents disk overflow. All API calls, trades, errors,
     and timing are logged.
  3. Database uses SQLAlchemy 2.0 with a repository pattern. Raw SQLAlchemy
     never leaks beyond the database/ package.
  4. Exchange uses ccxt as the primary driver with a BaseExchange ABC.
     Swapping to Kraken/Coinbase requires only a new adapter class.
  5. Indicators are stateless pure-function classes. Each accepts a DataFrame
     and returns a Series/DataFrame — no mutation of input data.
  6. Strategies enforce a strict interface: initialize/calculate/entry_signal/
     exit_signal/score. The backtesting engine works with any strategy.
  7. Risk management uses risk-based position sizing (fixed-fraction of max
     loss) and validates every trade before execution.
  8. Backtesting engine is event-driven, bar-by-bar. Includes stop-loss,
     take-profit, and trailing stop simulation.
  9. Paper trading mirrors the live trading interface — only the broker changes.
  10. Live execution (OrderExecutor) is guarded by PAPER_TRADING flag check at
      both the settings and BinanceClient level.

Decisões tomadas:
  - SQLite for development (zero-config, file-based, WAL mode enabled).
  - PostgreSQL support ready via DATABASE_URL env var.
  - ccxt preferred over python-binance for cross-exchange portability.
  - No global mutable state; settings singleton is frozen dataclass.
  - All secrets via .env; no hardcoded values anywhere.

Dependências adicionadas:
